# Instructions for AI agents working on this repository

Read README.md, CONTRIBUTING.md and DEVELOPMENT.md (file format, checks, proofs, automatic search) first. In short:

- Work on a new branch from the latest `main`; never push to `main`. Open one pull request per improvement.
- Never modify or delete a rule file with `"locked": true`. Add a new file with a new id instead.
- Before committing, run `python tools/build_atlas.py --base origin/main --changed`. It checks only the rules your change adds or modifies, not the earlier ones. Do not open a pull request unless it prints `OK`. The check in CI still verifies all rules.
- Do not weaken the checks in `tools/build_atlas.py` (tolerances, quality rules, locked check) to make a rule pass.
- New families: create `rules/<family_id>/family.json` with `name`, `short` and `description` in both `en` and `de`.
- If you change English texts (`i18n/en.json`, `content/en/`), update the German texts in the same pull request, then run `--sync-hashes`.
- Every reference you add must be checked to exist; never invent citations.
- Code conventions: pure Python, a single file per program, English comments, one statement per line.
- Every rule needs an interval proof: run `python tools/verify_rigorous.py --strict --merge reports/interval_proofs.json <rule files>` and commit the updated report with the rules. Never call a floating-point check a certificate or a proof; it is a numerical check.
- State in the pull request description what was computed, how it was proven, and what is still open.
- Tooltips on the website: never hover only (`title` alone). Every tooltip needs a clickable, keyboard-reachable ⓘ (or marker) in addition to hover, so it also works on touch screens; use the shared popup (`td .oq` / `th .hw` with `data-tip`).
- Exponents on the website: never Unicode superscript characters (⁰ ¹ ² ³ ⁴ … ⁻); depending on the font some of them slip down. In HTML use `<sup>`; in plain text (e.g. popups filled with `textContent`) write `10^-14` or `1e-14`.
- References in the atlas (`content/references.json`, the numbers `[n]` shown on the website, also in the column N_Lit): always sorted by year, oldest first, undated entries last. The number of a reference is its position. Add a new reference with its year anywhere and run `python tools/sort_references.py`; it sorts and renumbers every use of the numbers (documentation, families, `reference_data/literature_counts.json`). Then run `python tools/build_atlas.py --sync-hashes`. The build refuses an unsorted list. In the column N_Lit the earliest publication that reached a node count is credited (use the year of the cited source if a paper quotes an earlier one).
- Literature: if your change uses, tests or finds a publication, extend `literature.md` in the same pull request: put it in the right section (used / tried without gain / not used yet), sorted by date, with the citation, the link behind the `###` heading, a short note, and the abstract after `>`. The note says only how the work is used in the atlas (documentation, code, a family of rules, the column N_Lit) or, for a tried idea, what was tested and what came out. Never compare the numbers of the work with atlas rules in `literature.md` (the atlas changes), and never write where a file or text came from or how much of it was read (no "full text read", "supplement", "provided by", "only the abstract") (word for word only from arXiv, Crossref or open access; otherwise a short summary in your own words, or `> No abstract available`). Check every reference against its DOI or arXiv page; never invent a citation. Move an entry when its status changes.
